# SafeHer Backend — Build Guide

This is a **file structure + guide only** — no working code yet. It's meant to be
handed to a human (Prakash) or an agentic coding assistant (Claude Code, Cursor, etc.)
to fill in, following the plan below. Read this file first, then `ARCHITECTURE.md`,
then `API_CONTRACT.md` before writing any code.

## Why hybrid (Firebase + Django) instead of just one

The frontend is a Flutter app (SafeHer) with 5 tabs: Home, Journey, AI, Community, History.
Two of those tabs are **realtime-first** (Home's SOS, Journey's live tracking) and three
are **CRUD/relational-first** (Community reports, History records, AI logs). Forcing
either backend to do both jobs badly is the thing to avoid:

- **Firebase owns:** Auth (phone/OTP), realtime data (live journey location, SOS events),
  and push notifications (FCM). This is what Firestore's realtime listeners and FCM
  are built for — reimplementing that in Django means hand-rolling websockets.
- **Django (DRF) owns:** everything relational — Community incident reports with
  filtering/search, History (read-only aggregated records), and the AI tab's
  orchestration logic. This is what a real schema + admin dashboard is built for —
  doing this in Firestore means fighting NoSQL for queries like "incidents within 2km
  in the last 7 days."

The Flutter app talks to **both**: Firebase SDK directly for realtime/auth, and this
Django REST API for everything else. See `ARCHITECTURE.md` for the exact request flow.

```
safeher-backend/
├── manage.py

│   ├── settings.py
│   ├── urls.py
│   ├── asgi.py
│   └── wsgi.py
├── apps/
│   ├── accounts/             # user profile, emergency contacts, secret code
│   ├── journey/               # PAST journey summaries only — live tracking is Firestore
│   ├── community/            # incident reports, safety alerts, safety map pins
│   ├── history/               # read-only aggregated views over the other apps
│   ├── ai_assistant/          # AI chat, area safety scoring, route recommendations
│   │   └── services.py       # LLM/ML orchestration, kept out of views.py
│   └── core/                  # cross-app helpers
│       ├── firebase_auth.py  # verifies Firebase ID tokens from the Flutter app
│       ├── permissions.py
│       └── utils.py
├── firebase/
│   ├── service_account.json.example   # copy → service_account.json (gitignored), fill with real creds
│   └── firestore_schema.md            # collections Firebase owns — Django never writes these directly
└── tests/
```

Each app follows the standard DRF layout: `models.py` → `serializers.py` → `views.py` → `urls.py`,
plus `admin.py` so you get a free moderation dashboard for Community reports.

## Build order (do this in sequence, don't jump around)

1. **`config/settings.py`** — get a bare Django project running with DRF and `django-cors-headers` installed. SQLite is fine to start; switch to Postgres before anything resembling production.
2. **`apps/core/firebase_auth.py`** — get Firebase token verification working first. Every other endpoint depends on knowing who the user is. Test it against a real ID token generated by the Flutter app's Firebase Auth SDK.
3. **`apps/accounts/`** — user profile + emergency contacts. Simple CRUD, good first app to prove the auth flow end-to-end.
4. **`apps/community/`** — incident reports and safety alerts. This is the app with the most "real" relational logic (geo queries, filtering) — see `API_CONTRACT.md` for the field list.
5. **`apps/history/`** — mostly read-only serializers pulling from the other apps' models plus Firestore snapshots (see `firebase/firestore_schema.md` for how journey/SOS records land here).
6. **`apps/ai_assistant/`** — build `services.py` (the orchestration logic) before `views.py`. Decide which LLM/ML provider you're calling and stub that call first.
7. **Firestore side (not in this repo, done in Firebase Console + Flutter)** — set up the `journeys`, `sos_events`, and `fcm_tokens` collections per `firebase/firestore_schema.md`, and a Cloud Function that fires FCM on SOS write.

## What NOT to build here

- No live-location endpoints in Django — that's Firestore + the Flutter Firebase SDK directly.
- No websocket/channels setup unless you outgrow Firestore's realtime listeners (unlikely for this app's scale).
- No auth system of your own — Firebase Auth is the only source of truth for identity; Django just verifies its tokens.
